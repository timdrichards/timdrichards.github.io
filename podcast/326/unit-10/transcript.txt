Strip away the screens, and almost every app is a list of records that people make, look at, change, and throw away. A contact list. A to-do list. A shopping cart. A class roster. A set of blog posts. Each one is a collection of things, and the person using it wants to do the same four things to each thing. Those four are create, read, update, and delete, and the first letter spell crud. The name is worth having because it lets you check an app for gaps in a few seconds. For every kind of record in your project, ask four questions. Can I make one? Can I see one? Can I change one? Can I remove one? Your Notes app answered yes to three of those before this unit. The fourth is the one people notice first when it is missing, because fixing a mistake is the most ordinary thing anyone does with something they have written. The four operations are older than the web. They are what every database has always offered. The database language SQL from the 1970s spells them insert, select, update, and delete. The acronym crud is usually credited to James Martin's 1983 book on database design, and it's spread because it gave programmers one word for the plain core of a program that handles data. HTTP picked up the same four ideas as methods. Get and post came first. Rout and delete were defined in HTTP version 1.1, whose first specification appeared in January 1997. Around the year 2000, Roy Fielding's dissertation described REST, a way of designing web services where every record has its own URL, and the method says what to do to it. That is exactly the shape of the route you are about to write. The URL names one entry, entry slash three, for example. The method says what happens to it, get reads it, put replaces it, delete removes it. Once you see that pattern, you can guess most of an unfamiliar API just from its list of URLs. So what does the new route look like? It is a fourth route in your entries router matched to the same ID pattern your delete route already uses. And it does the same four steps as every other route in that file. Read the file, parse it into an array, do one thing to the array, write the array back. The one thing this time is replacement. Create pushes a new entry onto the end of the array, delete splices one out, update assigns a new value to a position, so whatever sat there is replaced, that really is the whole difference. There are two checks before the replacement happens. First, is there an entry at that ID at all? If not, the server answers with a 404, not found. Second, are the new values any good? For that you reuse the validate entry function from unit 09 exactly as written. If the title or body is missing, the server answers with a 400, bad request, and the same message the create form already shows. Notice that you did not write any new validation code. The function that guards create now guards update to because both are really asking the same question. Is this a well formed entry? That is the payoff of pulling validation into one function back in unit 09, a fourth route and zero new checks. And like every route in the file, the new one goes through the async handler wrapper. So the form always starts from what is actually on the page instead of trying to read it back out of the displayed text. Here is a detail that matters more than it looks. Each input in that form is created on its own and its value is set as plain text. It is not written into one long string of HTML. Why does that matter? Because a title is whatever someone typed and people type double quotes. If you glue a title into a string of HTML, a title like he said, quote, high, quote, ends the attribute at the first quote, the edit form opens showing only the words he said and saving it quietly throws the rest away. A title written to close the tag can go further and run as code in the page. Setting the value as text avoids all of that quotes and all. The same rule applies when the saved entry goes back on the page. Its title and body are set as text content, never as HTML. If you remember one sentence from this section, make it this one. Never build HTML out of what someone typed. When you press save, the page sends a put request with fetch, carrying the new title and body as JSON. The same 5 second limit from unit 08 applies, so a server that never answers ends in an error instead of a page that waits forever. If the save works, the form is swapped back for the updated entry with no page reload. If it fails for any reason, the page says so, leaves the form open with your changes still in it and lets you try again. Cancel is the simple one. It puts the original entry back and sends nothing to the server at all. So there are only two ways out of the edit form and only one of them talks to the server. Put carries one more idea worth having a word for. The word is EOIDEMPATENT. It means that sending the exact same request again leaves things in the same state as sending it once. Send the same put five times and the entry ends up exactly as it would after one. Send the same post five times and you have five entries. That difference is not trivia. It decides what a client is allowed to do when something goes wrong. Picture a phone on a weak signal. It sends a request and the connection drops before the answer comes back. Did the server get it? The phone cannot tell. If the request is idempotent, it can simply send it again because repeating it changes nothing. If it is not, sending it again might create a second record so the client has to stop and ask the person. That is why browsers and libraries will quietly retry some requests and never others. You might wonder why the edit form uses fetch at all when Unit 08 showed a classic form that works with no JavaScript. The answer is a limit in HTML itself. An HTML form can only send get or post. If you write method equals put on a form, the browser does not complain. It quietly sends a get instead. Server rendered frameworks work around this with something called a method override. The form sends a post with a hidden field often named underscore method that says what it really means. A small piece of middleware on the server reads that field and treats the request as a put or a delete before the routes see it. You will not need it in this course, but you will see underscore method in other people's code and now you know why it is there.
