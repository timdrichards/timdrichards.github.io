Unit 10: CRUD Against a File

The audio companion to Unit 10. Your entries app can create, read and delete, but it cannot change an entry once it exists. This episode covers adding the update route with PUT, building an inline edit form safely, what idempotent means and why it matters when a request fails, why a plain HTML form cannot send PUT, and the one honest limit of using array positions as ids.

Why CRUD exists

1:23A contact list.

1:25A to-do list.

1:26A shopping cart.

1:27A class roster.

1:29A set of blog posts.

1:31Each one is a collection of things, and the person using it wants to do the same four things to each thing.

1:37Those four are create, read, update, and delete, and the first letter spell crud.

1:42The name is worth having because it lets you check an app for gaps in a few seconds.

1:47For every kind of record in your project, ask four questions.

1:51Can I see one?

1:52Can I change one?

A short history

2:11The four operations are older than the web.

2:13They are what every database has always offered.

2:17The database language SQL from the 1970s spells them insert, select, update, and delete.

2:25The acronym crud is usually credited to James Martin's 1983 book on database design, and it's spread because it gave programmers one word for the plain core of a program that handles data.

2:38HTTP picked up the same four ideas as methods.

2:43Get and post came first.

2:45Rout and delete were defined in HTTP version 1.1, whose first specification appeared in January 1997.

2:54Around the year 2000, Roy Fielding's dissertation described REST, a way of designing web services where every record has its own URL, and the method says what to do to it.

3:05That is exactly the shape of the route you are about to write.

3:09The URL names one entry, entry slash three, for example.

3:14The method says what happens to it, get reads it, put replaces it, delete removes it.

3:20Once you see that pattern, you can guess most of an unfamiliar API just from its list of URLs.

Adding the update route

3:28So what does the new route look like?

3:31It is a fourth route in your entries router matched to the same ID pattern your delete route already uses.

3:37And it does the same four steps as every other route in that file.

3:41Read the file, parse it into an array, do one thing to the array, write the array back.

3:49The one thing this time is replacement.

3:51Create pushes a new entry onto the end of the array, delete splices one out, update assigns a new value to a position, so whatever sat there is replaced, that really is the whole difference.

4:05There are two checks before the replacement happens.

4:08First, is there an entry at that ID at all?

4:12If not, the server answers with a 404, not found.

4:16Second, are the new values any good?

4:19For that you reuse the validate entry function from unit 09 exactly as written.

4:25If the title or body is missing, the server answers with a 400, bad request, and the same message the create form already shows.

4:35Notice that you did not write any new validation code.

4:38The function that guards create now guards update to because both are really asking the same question.

4:45Is this a well formed entry?

4:47That is the payoff of pulling validation into one function back in unit 09, a fourth route and zero new checks.

4:56And like every route in the file, the new one goes through the async handler wrapper.

5:02If something goes wrong inside it, say the JSON file no longer parses or the right fails, the error reaches your error handling middleware and comes back as a 500.

5:14The server keeps running instead of crashing.

Editing on the page

5:18On the page, editing needs something the user did not have before, a form for an entry that already exists.

5:25Rather than sending them to a whole new page, the app swaps the entries text for a small form right where it sits in the list filled in with the current title and body.

5:42Each list item carries them in two data attributes, data title and data body set when the page renders and updated after every save.

5:52So the form always starts from what is actually on the page instead of trying to read it back out of the displayed text.

6:00Here is a detail that matters more than it looks.

6:11It is not written into one long string of HTML.

6:17Because a title is whatever someone typed and people type double quotes.

6:22If you glue a title into a string of HTML, a title like he said, quote, high, quote, ends the attribute at the first quote, the edit form opens showing only the words he said and saving it quietly throws the rest away.

6:38A title written to close the tag can go further and run as code in the page.

6:44Setting the value as text avoids all of that quotes and all.

6:49The same rule applies when the saved entry goes back on the page.

6:53Its title and body are set as text content, never as HTML.

6:58If you remember one sentence from this section, make it this one.

7:02Never build HTML out of what someone typed.

7:06When you press save, the page sends a put request with fetch, carrying the new title and body as JSON.

Idempotent

7:52Put carries one more idea worth having a word for.

7:54The word is EOIDEMPATENT.

7:57It means that sending the exact same request again leaves things in the same state as sending it once.

8:06Send the same put five times and the entry ends up exactly as it would after one.

8:12Send the same post five times and you have five entries.

8:16That difference is not trivia.

8:18It decides what a client is allowed to do when something goes wrong.

8:23Picture a phone on a weak signal.

8:25It sends a request and the connection drops before the answer comes back.

8:29Did the server get it?

8:31The phone cannot tell.

8:32If the request is idempotent, it can simply send it again because repeating it changes nothing.

8:39If it is not, sending it again might create a second record so the client has to stop and ask the person.

8:45That is why browsers and libraries will quietly retry some requests and never others.

Why a plain form cannot do this

8:52You might wonder why the edit form uses fetch at all when Unit 08 showed a classic form that works with no JavaScript.

9:01The answer is a limit in HTML itself.

9:05An HTML form can only send get or post.

9:08If you write method equals put on a form, the browser does not complain.

9:14It quietly sends a get instead.

9:18Server rendered frameworks work around this with something called a method override.

9:22The form sends a post with a hidden field often named underscore method that says what it really means.

9:30A small piece of middleware on the server reads that field and treats the request as a put or a delete before the routes see it.

9:38You will not need it in this course, but you will see underscore method in other people's code and now you know why it is there.

One honest limit

9:47There is one thing this version of the app gets wrong and the unit says so plainly.

9:53Right now an entry's id is just its position in the array.

9:57Delete an entry and every entry after it moves down one place.

10:03Inside one browser tab, the code renumbers the list after a delete so everything stays in step.

10:09But a second tab does not know anything changed.

10:13An edit form left open there still holds the old position.

10:17Save it and it can land on whichever entry has moved into that spot and overwrite it.

10:23The home exercise has you handle the case the server can detect the entry your editing is gone, the save comes back 404 and the page should remove that stale entry instead of leaving a form with nowhere to go.

10:38The real fix comes in unit 12 when every entry gets an id from the database that never changes when other entries are deleted.
